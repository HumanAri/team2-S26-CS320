# Backend Documentation

This backend is a small FastAPI service that handles:

- Google OAuth login for `@umass.edu` accounts
- Email/password signup and login for `@umass.edu` accounts
- JWT-based session validation
- Early onboarding flows such as profile picture, categories, friend requests, and privacy settings
- Supabase reads/writes for app data

The main application lives in [main.py](/Users/jaredc./320/team2-S26-CS320/backend/main.py) and the Supabase client is initialized in [database.py](/Users/jaredc./320/team2-S26-CS320/backend/database.py).

## Stack

- FastAPI
- Uvicorn
- Supabase Python client
- `python-jose` for JWTs
- `bcrypt` for password hashing
- `requests` for the Google userinfo call

## Project Layout

```text
backend/
├── main.py           # FastAPI app and all current routes
├── database.py       # Supabase client setup
├── requirements.txt  # Python dependencies
└── .env              # Local backend env vars (not committed)
```

## Environment Variables

Create `backend/.env` with:

```env
GOOGLE_CLIENT_ID=your-google-oauth-client-id
JWT_SECRET=your-jwt-secret
ALLOWED_ORIGINS=http://localhost:5173
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_KEY=your-supabase-service-or-anon-key
```

Notes:

- `ALLOWED_ORIGINS` is comma-separated and defaults to `http://localhost:5173`.
- `JWT_SECRET` is used to sign the app's own bearer tokens.
- `GOOGLE_CLIENT_ID` is used to verify that a Google token belongs to this app.
- `SUPABASE_URL` and `SUPABASE_KEY` are loaded by `database.py`.

## Auth Model

Most protected routes expect:

```http
Authorization: Bearer <jwt>
```

That JWT is generated by this backend after Google login or regular email/password login. The current token payload may include fields like:

- `email`
- `first_name`
- `last_name`
- `google_id`
- `display_name`
- `profile_picture`
- `exp`

Token validation is handled by `get_current_user()` in `main.py`.

## Current API Surface

### `POST /api/auth/google`

Logs a user in with a Google access token by calling Google's `userinfo` endpoint.

Request body:

```json
{
  "token": "google-access-token"
}
```

Behavior:

- Rejects invalid Google tokens with `401`
- Rejects non-`@umass.edu` emails with `403`
- Creates a `users` row if the Google account has not logged in before
- Creates a default semester for first-time users
- Returns a signed app JWT plus profile data

Response fields:

- `token`
- `semester_id`
- `google_id`
- `email`
- `email_verified`
- `display_name`
- `first_name`
- `last_name`
- `profile_picture`

### `GET /api/auth/verify`

Protected route that returns:

```json
{
  "valid": true
}
```

Use this to confirm whether a stored JWT is still valid.

### `GET /api/auth/me`

Protected route that returns the current user info from the decoded JWT instead of refetching from Google.

Response fields may include:

- `google_id`
- `email`
- `email_verified`
- `display_name`
- `first_name`
- `last_name`
- `profile_picture`

### `POST /api/auth/signup`

Registers a non-Google account.

Request body:

```json
{
  "name": "Jane Doe",
  "email": "jdoe@umass.edu",
  "password": "plain-text-password"
}
```

Behavior:

- Rejects non-`@umass.edu` emails with `403`
- Rejects duplicate emails with `409`
- Hashes the password with `bcrypt`
- Stores the hash in `users.hashed_pw`
- Creates a default semester for the new user
- Returns a signed app JWT

Response fields:

- `token`
- `user_id`
- `semester_id`

### `POST /api/auth/login`

Logs a non-Google account in with email/password.

Request body:

```json
{
  "email": "jdoe@umass.edu",
  "password": "plain-text-password"
}
```

Behavior:

- Returns `401` if the user is missing
- Returns `401` if the password does not match the stored bcrypt hash
- Returns a signed app JWT on success

Response fields:

- `token`
- `email`

### `PATCH /api/users/pfp`

Protected route for onboarding step 1.

Request body:

```json
{
  "pfp": "🙂"
}
```

Behavior:

- Updates `users.profile_picture` for the authenticated user
- Returns `404` if the user cannot be found

### `POST /api/categories`

Protected route for onboarding steps 2 and 3.

Request body:

```json
{
  "semester_id": "semester-uuid",
  "categories": [
    {
      "name": "Homework",
      "color": "#FFB703",
      "priority": 1
    }
  ]
}
```

Behavior:

- Looks up the authenticated user by email
- Inserts one row per category into `categories`
- Uses the provided `semester_id` for every inserted category

### `POST /api/friends/requests`

Protected route for onboarding step 4.

Request body:

```json
{
  "friends": ["friend@umass.edu", "Alex Smith"]
}
```

Behavior:

- Finds the authenticated sender in `users`
- Tries to resolve each friend first by `email`, then by `display_name`
- Inserts pending friendships with `status = 0`
- Returns which entries were sent and which were not found

Example response:

```json
{
  "sent": ["friend@umass.edu"],
  "not_found": ["Alex Smith"]
}
```

### `PATCH /api/users/privacy`

Protected route for onboarding step 5.

Request body:

```json
{
  "share_goals": true,
  "share_results": true,
  "share_other": false,
  "share_all": false
}
```

Behavior:

- Updates the authenticated user's privacy flags in `users`
- Returns `404` if the user cannot be found

## Expected Supabase Tables

This code assumes at least these tables exist:

- `users`
- `semesters`
- `categories`
- `friendships`

Based on current usage, the code expects columns similar to:

- `users`: `id`, `google_id`, `email`, `email_verified`, `display_name`, `first_name`, `last_name`, `profile_picture`, `hashed_pw`, `share_goals`, `share_results`, `share_other`, `share_all`
- `semesters`: `id`, `user_id`, `name`, `start_date`, `end_date`, `created_at`
- `categories`: `user_id`, `semester_id`, `name`, `color`, `priority`
- `friendships`: `user1_id`, `user2_id`, `status`

## Current Behavior Notes

- New users automatically get a semester based on the current month:
  - January through June: `Spring <year>`
  - July through December: `Fall <year>`
- JWTs expire 8 hours after issue.
- CORS origins are controlled through `ALLOWED_ORIGINS`.
- Google login validates token audience only if the Google response includes an `aud` field.
- Several onboarding endpoints currently perform the update/insert and rely on FastAPI's default `200 OK` response without returning a custom body.

## Known Gaps

These are worth knowing while working on this branch:

- There is no dedicated health check route.
- There is no logout or token revocation flow.
- There is no schema migration file in `backend/`; the Supabase schema is assumed to already exist.
- The backend currently mixes authentication, onboarding, and data access logic in a single `main.py` file.
